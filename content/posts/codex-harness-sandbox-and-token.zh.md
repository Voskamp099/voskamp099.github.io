沙箱和令牌：两层隔离各管一件事

"给 agent 加隔离"这句话里其实藏着两个互不替代的问题。把这分开，配置才写得清楚，出问题的时候也才知道该查哪一层。

- **能写这台机器上的哪些目录？** 这是本地沙箱管的事。
- **能改 GitHub 上的哪个仓库？** 这是凭据管的事。

提示词和项目说明文件两层都管不了。前者是行为指令，后者是写给人看的约定；两者都可能被遵守，也都可能被无视。真正管事的是权限。

## 一、第一层：本地沙箱在技术上做了什么

Codex 在 macOS 上用 Seatbelt，在 Linux 上用 bubblewrap 加 seccomp，在 Windows 上有原生的沙箱实现。思路是同一件事：给 agent 一个有边界的执行环境，命令继承这个边界，而不是靠提示词劝它别乱来。

沙箱模式有三档：

- read-only：能读，不能写。
- workspace-write：工作目录内可写，工作目录外只读。这是日常开发的档位。
- danger-full-access：没有边界。

可写范围具体是三块：当前工作目录、系统临时目录、以及环境变量指向的临时目录。目录之外的所有内容都可以读，只是不能改。

还有一类路径即使在可写范围内也保持只读，而且是递归的：.git、.agents、.codex、.aws。这个设计有实际理由——它们分别存着版本历史、agent 自己的状态和云凭据，允许 agent 随手改写等于让沙箱形同虚设。但它带来一个直接后果，我在下一节说。

审批策略是另一件事，它不改变边界，只决定越界的时候发生什么：

- on-request：越界时弹出问题。
- never：越界时命令直接失败，错误回给模型。

## 二、实测：同一个动作，三种结果

我在沙箱里逐条试过，下面每一行都是实际输出，不是设计文档里的描述：

| 动作 | 结果 |
| --- | --- |
| 在工作目录里新建文件 | 成功 |
| 读工作目录之外的文件 | 成功，可以读 |
| 在工作目录之外新建文件 | Operation not permitted |
| 在另一个项目目录里新建文件 | Operation not permitted |
| 往系统临时目录写文件 | 成功 |
| 在沙箱里 git add | 失败：无法创建 .git/index.lock |
| 在沙箱外 git add 加 git commit | 成功 |

前三行和第四行合起来就是"目录内可写、目录外只读"这句话的完整含义，包括目录外仍然可读这一条。

最后两行是这一层真正的坑：沙箱把 .git 设成只读，所以普通提交在沙箱内必然失败。要既保留沙箱又能提交，办法是规则文件：给 git 的写类子命令一条允许规则，让这些命令在沙箱外执行且不提示。

## 三、第二层：仓库级凭据

第一层管不到远端。会话可以读本地任何文件，也可以发网络请求，所以本地边界本身并不限制它能改 GitHub 上的哪个仓库。那是凭据的事。

做法是一个仓库一枚细粒度个人访问令牌，令牌的仓库访问范围只写那一个仓库，权限按需要给到最小。令牌存在仓库外的凭据目录里，目录权限 700，文件 600。

启动会话时，工具把这一枚令牌注入环境变量，命令行工具和 git 都会用它：git 的凭据助手在环境变量存在时优先用环境变量里的令牌，而不是钥匙串里那枚全局登录。这一点是整套设计的支点，因为机器级登录通常能碰到账号能看到的每一个仓库，那正好是要消除的越权面。

没有对应令牌的会话不会退回那枚全局登录。我让它拿到一个占位值，于是 GitHub 调用直接失败，而不是悄悄用上一枚范围过大的令牌。失败比"成功但范围不对"好排查。

于是第二层真正提供的是：即使沙箱被绕过、即使模型被诱导，这个会话手上的令牌也只能改一个仓库，而且那个仓库就是它被授权的那个。

## 四、两层为什么不能互相替代

| 想要的效果 | 靠哪一层 |
| --- | --- |
| 不许改别的目录 | 沙箱 |
| 不许读别的目录 | 做不到，沙箱按设计允许读 |
| 不许改别的仓库 | 令牌范围 |
| 不许把本机内容发到外部 | 沙箱挡不住，要靠网络策略和凭据不出现在输出里 |
| 不许违反项目约定 | 提示词与项目说明文件，只能靠自觉 |

最后一行值得强调：写进项目说明文件里的"不要访问无关仓库"是一条请求，不是一道锁。令牌才是锁。

## 五、剩下的口子

这套东西有明确的边界，说清楚比装看不见好。

**读是全的。** 沙箱允许读机器上的任何文件。目录外的文件只是不能改，不能被排除在读取之外。所以真正的敏感文件，隔离要靠操作系统或靠根本不在那个身份下。

**令牌在环境变量里。** 环境变量会被子进程继承，也可能被打印出来。我把会打印凭据的命令逐个禁掉：打印环境、打印单个环境变量、打印 GitHub 令牌、打印 git 凭据。这只是降低概率，不是消除风险；真正的兜底是令牌本身的范围小、有效期短。

**网络是开的。** 日常开发要推送、要调接口，所以沙箱里开着出网。这意味着会话能读到的内容也可能被发出去。可写范围限制了它能改什么，限制不了它能传什么。要收紧就得关掉网络，再用白名单单独放行需要的域名。

**同一台机器，同一个身份。** 沙箱和令牌都是在同一个系统用户下做的边界。它们适合挡误操作和范围蔓延，不等于隔离。真要"完全够不到"，得换系统用户、容器或虚拟机。

## 六、一份可复制的检查清单

配置完之后，值得自己跑一遍：

1. 在工作目录里写一个文件，应该成功。
2. 在工作目录外写一个文件，应该失败，并且失败里没有审批问题。
3. 读工作目录外的文件，应该成功。
4. 在另一个项目目录里写文件，应该失败。
5. 提交一次，应该成功。这一条失败就说明命令规则没有生效。
6. 打印一次环境变量，应该被拒绝。
7. 用这个会话访问它不该碰的仓库，应该失败。

前六条在几分钟内跑完。最后一条是这套配置存在的理由，值得单独确认一次。
