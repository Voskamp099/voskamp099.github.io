一个项目一个工作区

我把 Codex CLI 的用法定成了一条规矩：每个项目一个文件夹，一个文件夹一个会话。会话可以写自己的目录，可以读机器上的任何地方，但写不到目录外面去；而且它不会再弹审批框等我点头。

这条规矩不是审美偏好，是三个具体的麻烦逼出来的。

**上下文会串。** 一个会话里聊过的东西会一直跟着，换项目时它还带着上一个项目的判断和上下文，最后开始拿旧结论解释新代码。

**目录会越界。** 会话的工作目录是当前目录，但它能读到别处的文件，于是别处的结论会被当成当前项目的事实。

**凭据会越权。** 一台机器上的 GitHub 登录通常能碰到所有仓库，于是"这个项目不该碰的仓库"其实随时能碰。

这三件事的共同点是：它们都不是靠一句提示词能解决的。提示词是行为指令，目录和凭据是权限边界。要真正把边界做实，得从文件系统这一层开始。

## 一、三层结构

我最后落到三层，每一层管一件事，互相不重叠：

| 层 | 放在哪 | 决定什么 |
| --- | --- | --- |
| 工作区边界 | 用户配置加每个项目一个 profile | 哪些目录可写 |
| 命令规则 | rules 目录下的规则文件 | 哪些命令允许离开沙箱，哪些打印凭据的命令直接拒绝 |
| 仓库级身份 | 项目清单加一个只存 token 的目录 | 这个会话能碰到 GitHub 上的哪个仓库 |

第一层是 Codex 自带的沙箱；第二层是同一个沙箱的例外与禁令；第三层完全在 Codex 之外，靠的是每个仓库一枚单独的凭据。

## 二、配置文件长什么样

用户配置里只写默认值：

```toml
approval_policy = "never"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = true
writable_roots = []
```

`approval_policy = "never"` 是关键。我的审批习惯是"越界的一律不批"，那么弹窗本身就没有信息量，只会把一次失败变成一次等待。设成 never 之后，越界写入不再是一个问题，而是一个错误：错误直接回到模型那里，模型自己看到失败，然后改路线。

每个项目一个 profile 文件，只写跟默认不同的部分，外加这个目录的信任状态：

```toml
model = "gpt-6-luna"
approval_policy = "never"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = true
writable_roots = []

[projects."~/code/agent-eval"]
trust_level = "trusted"
```

profile 是叠加在用户配置之上的一层，同名键以 profile 为准。所以"每个项目一份权限配置"这件事，不需要任何自造机制，Codex 自己就有。

命令规则住在 rules 目录里，语法像 Python：

```python
prefix_rule(pattern=["git", "commit"], decision="allow",
            justification="Local commit is covered by the standing authorisation.")
prefix_rule(pattern=["printenv"], decision="forbidden",
            justification="Printing the environment would expose the scoped token.")
```

allow 的意思是"这条命令允许在沙箱外执行，而且不提示"；forbidden 的意思是"这条命令直接拒绝"。多条规则同时命中时取最严格的那个。

项目清单把目录、profile 和仓库绑在一起：

```toml
[projects.agent-eval]
path = "~/code/agent-eval"
profile = "agent-eval"
repo = "example/agent-eval"
```

我另外写了一个小启动器，把这三件事一次做完：选 profile、把工作目录指过去、把这一枚仓库级 token 注入环境。终端里敲一个名字就能开工。

## 三、实测

我用一个临时仓库把边界跑了一遍，三条命令，三种结果：

| 命令 | 结果 |
| --- | --- |
| 在工作目录里写文件 | 成功 |
| 往工作目录之外的目录写文件 | 失败，Operation not permitted，错误回给模型，没有弹窗 |
| git add 加 git commit | 成功 |

第二行是关键：失败是"当场失败"，不是"问一下再失败"。

## 四、五个坑

**一、workspace-write 里的 .git 是只读的。** 这条我是在沙箱里直接试出来的：git add 报 `Unable to create '.git/index.lock': Operation not permitted`。也就是说，普通提交在沙箱内是跑不通的。解法是规则文件里给 git 的写类子命令加 allow，让它们在沙箱外执行、不提示。这样既能提交，又不用把整个会话放到无沙箱状态。

**二、never 不是"少弹窗"，是"越界即错误"。** 这一点值得单独说，因为它决定了失败长什么样。on-request 下，越界会变成一次等待；never 下，越界变成一次命令失败。两者都拦得住写入，但后者不会占用人的注意力，也不会让人误以为"点一下就能过"。

**三、临时目录属于可写区。** 会话状态里写得很清楚：可写范围是工作目录、临时目录和系统临时目录。所以"目录外一律只读"这句话在临时目录上是例外。临时目录里写的文件不是对任何项目的改动，但它确实不是只读的。

**四、规则的前缀是逐个参数精确匹配的。** 我一开始想用一条规则挡住整个凭据目录，结果没生效。原因是模式里的每个元素都要和命令的参数逐个精确相等，目录前缀不会像通配符那样生效。结果是我把真正会打印凭据的四条命令逐个禁掉了：打印环境、打印环境变量、打印 GitHub token、打印 git 凭据。

**五、命令行和桌面端的模型目录不是一回事。** 桌面端默认的模型，命令行用同一个账号去请求会被后端拒掉，表现为每次请求都报模型不存在。profile 里自己钉一个能答的模型就解决了。这一条和隔离无关，但它会让你以为整套配置坏了。

## 五、加一个新项目

三步：

1. 项目清单里加一条：目录、profile、仓库。
2. 仓库里按最小权限生成一枚细粒度令牌，存在仓库外的凭据目录，权限只给当前用户可读。
3. 启动器敲名字开工。

令牌不进仓库，不进提示文件，不进提交信息，也不进日志。

## 六、还没解决的部分

这套配置能做到的是：会话写不进别的目录，拿不到别的仓库的令牌。

它做不到的是"技术上完全够不到"。如果一个仓库真的不能被这个项目碰到，那么令牌这一层必须由操作系统来兜底——独立的系统用户、容器或者虚拟机，把那个目录从另一个身份下彻底隔开。沙箱和令牌是在同一台机器、同一个用户身份内做的边界，适合挡误操作和范围蔓延，不适合当真正的隔离。

我的取舍是：日常开发用目录加沙箱加仓库级令牌；真正不能被碰的东西，换一个系统用户或一台机器。
