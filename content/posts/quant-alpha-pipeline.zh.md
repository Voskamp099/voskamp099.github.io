最早我做的事情很朴素。在 WorldQuant BRAIN 的网页上找数据集、挑字段、写表达式、点 simulate，等结果出来，看 Sharpe 和 fitness 够不够，够了就提交。

平台有一套自己的门槛：Sharpe 要过 1.25，fitness 要过 1.0，换手、权重集中、子池 Sharpe 都会单独判。第一次提交成功的时候挺开心的，但很快发现问题——这条路太慢了。

一次模拟要排队等结果，一个想法要试几个字段、几组窗口、几种算子组合，手动点下来一个下午就过去了。而且所有东西只存在于网页上，关掉页面，实验记录就没了。

## 把研究搬进 VSCode

下一步是把研究搬到本地，写脚本做四件事：登录、发起仿真、轮询结果、把指标写进 CSV。

搬进去以后，最大的变化不是速度，而是可追溯。每一次模拟的表达式、参数、返回的 alpha id 和全部指标都落在本地文件里，可以随时回看，也可以断点续跑。

平台对请求频率有限制，所以脚本里加了一个全局请求闸门：所有研究进程共用一个文件锁，保证每次请求之间至少隔两秒，撞到限频就按 Retry-After 退避。这部分不是优化，是必须的——账号被限流之后会有一段时间什么都做不了。

## 让 Agent 跑起来

有了脚本之后，我开始用 Agent 来驱动。关键不是让 AI 写代码，而是先把工作分层，让 Agent 知道该动哪一层：

- **配置面**：region、universe、窗口、算子、交互对、门槛。改一个 JSON 文件就行，不用碰代码。
- **单格手术**：加一种新变换、改一段逻辑。Agent 只动那一个 cell。
- **新增 stage**：加一整个新环节，比如多窗口稳健性检查。Agent 新增 cell，不破坏旧逻辑。
- **重构**：几乎不触发，先对齐方案。

绝大多数想法落在前两层。这样我和 Agent 的对话就变成了一句话："我想试 momentum 配 earnings revision 的交叉。"Agent 回答应该改哪个文件，然后直接改。

中间保留了一道人工闸：机器可以拉字段库、按覆盖率筛选，但哪些字段值得测、往哪个方向测，还是我拍板。我只勾一份三十多行的短名单，其余交给机器。

## Alpha 分类分析

自动跑起来以后，遇到了一个新问题：跑出来的 alpha 太多，看不过来。几百条候选停在样本内阶段，最终只有五十来条进了正式提交。逐条读不现实。

所以后来加了一步，把表达式按经济含义拆成"腿"，再做统计。一条 alpha 通常是两到三条腿的组合，比如"负债相对市值 + 经营现金流相对资产"，或者"跌得多且放量 + 期权隐含波动偏斜"。拆开之后统计频次，能看到很清楚的结论：

- 整套组合其实只建立在十四类信号上，其中复用最多的是期权隐含波动偏斜和短窗反转。
- 评级几乎完全由 fitness 决定，跟 Sharpe 关系不大——换手一高，Sharpe 再好也会掉档。
- 失败原因高度集中：fitness 不达标占 64.7%，Sharpe 不达标占 53.5%，其余是子池不稳、权重集中和换手过高。
- 有两百多条通过了平台的全部检查，只是因为和已有持仓太像，没有提交。

最后一条最重要。两百多条候选越过了平台门槛，最后只有五十来条进得去。真正卡住的不是 Sharpe 门槛，而是组合里的正交性预算。

## 现在到哪了

方法上大致跑通了：手动起步，脚本接管，Agent 驱动，最后用分类分析收口。

还没解决的是来源问题。已提交组合的自相关中位数 0.68，贴着重复度的上限。下一阶段的增量不会来自再做一遍组合搜索，而来自找到真正还没被用过的信息源。

具体到哪些字段、每条 alpha 的完整指标和失败明细，我留在本地，没有公开。
